# Firefox behavior and capture validation

The current capture gate uses a clean Mozilla Firefox binary downloaded from
the official release service, not an optional Firefox package from the
development checkout. `fetch-firefox-reference.sh` follows the official
redirect, verifies the archive digest, records the version in
`REFERENCE-MANIFEST`, and caches the extracted tree only under the ignored
object directory. The latest audited reference is Mozilla Firefox 154.0
(`firefox-154.0.tar.xz`, archive SHA-256
`7665cd49ab13417270748325838e565136adbc76d41bbd76fb24d15a0cc7792b`).
NaiveFox is built from the pinned Firefox snapshot in this repository, so
exact ClientHello/HTTP/2 SETTINGS equality is reported rather than required;
Necko/NSS ownership, protocol, marker, and multiplexing assertions remain
strict.

The comparison runs against the same loopback-only Caddy HTTPS front-end and
is generated by:

```bash
netwerk/naivefox/test/integration/run-capture-comparison.sh
```

The runner requires `dumpcap`, `tshark`, and loopback capture permission. On a
development machine where `dumpcap` has no capabilities, grant only the normal
Wireshark capture capabilities once:

```bash
sudo setcap cap_net_raw,cap_net_admin=eip "$(command -v dumpcap)"
```

The ordinary Firefox reference performs one headless HTTPS navigation to the
fixture front-end. NaiveFox keeps one process alive while two SOCKS requests
create separate HTTP/2 CONNECT streams. Each side receives an independent
private TLS key log so tshark can inspect encrypted HTTP/2 without substituting
another TLS or H2 implementation. The official tarball has no source objdir;
the optional `NAIVEFOX_CAPTURE_REFERENCE_OBJDIR` check is skipped for it.

This is the privileged, decrypted internal-stack audit. The complementary
passive test without TLS keys is documented in
[`OBSERVER-TRAFFIC-REPORT.md`](OBSERVER-TRAFFIC-REPORT.md).

## Data handling

Packet captures, TLS secrets, copied NSS profiles, screenshots, and raw process
logs are sensitive. They are created with mode `0700`/`0600` only under the
ignored object directory. On success they are deleted after safe aggregates
have been produced. On failure the private directory is preserved and its path
is printed for local diagnosis.

The safe output contains only:

- ordered ClientHello cipher, extension, group, signature, version, and ALPN
  identifiers;
- selected ALPN;
- HTTP/2 SETTINGS identifiers and values;
- early SETTINGS, WINDOW_UPDATE, and HEADERS frame metadata;
- request methods and numeric TCP/H2 stream identifiers;
- header names for the synthetic-marker and Naive-padding checks.

It never contains `Proxy-Authorization`, header values, credentials, TLS
secrets, DATA frames, or tunneled payload.

## Comparison record

The current local comparison was recorded on 2026-08-20. Application request
differences are expected: ordinary Firefox sends `GET`, while NaiveFox sends
`CONNECT`. The executable, `libxul`, and NSS hashes differ because the
reference is the official Firefox release while NaiveFox uses the pinned
project snapshot. That difference is expected and is recorded, not hidden.

| Measure | Expected | Actual |
|---|---|---|
| Build provenance | Official Mozilla Firefox 154.0 archive; digest recorded in manifest | Pinned NaiveFox Firefox snapshot; independent hashes recorded |
| TLS endpoint and SNI | Same fixture `localhost` front-end | Same `localhost` front-end |
| Ordered ClientHello ciphers | Firefox-owned configuration; no alternate TLS stack | Compared and reported; equality is not required across releases |
| Ordered TLS extension types | Firefox/NSS behavior on both paths | Compared and reported; independent NSS randomization/version drift is expected |
| Supported groups and signatures | Firefox/NSS behavior on both paths | Compared and reported; no replacement TLS stack observed |
| ALPN offer and selection | `h2` selected on both paths | `h2` selected on both paths |
| Client HTTP/2 SETTINGS | Firefox-owned values and ordering | Compared; equality is diagnostic across releases |
| Early frame order | Firefox preface, SETTINGS/WINDOW_UPDATE, then request HEADERS | Observed on both paths |
| Connection-level WINDOW_UPDATE | Firefox-owned increment and placement | Firefox-owned values observed on both paths |
| Application method | Reference `GET`; NaiveFox `CONNECT` | Reference `GET`; NaiveFox `CONNECT` |
| NaiveFox connection reuse | Two CONNECT stream IDs on one outer TCP stream | 2 requests, 1 TCP stream, 2 H2 stream IDs |
| Naive padding header name | Present on Naive-compatible CONNECT exchange | Present in request and response directions |
| Synthetic `ALPN`/`Upgrade`/`Connection` marker | Absent | Absent |
| Wire-stack provenance | Necko HTTP/2 and NSS TLS, not a replacement stack | Official Firefox reference and NaiveFox both use Firefox networking primitives |

NaiveFox disables the separate socket process for this in-process prototype.
That changes process placement and protocol scope, but does not replace
Firefox's Necko/NSS wire implementation. The strict H3 equivalent uses the
same official-reference policy; see `H3-CAPTURE.md`.
